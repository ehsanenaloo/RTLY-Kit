شش اعتبارسنج#

RTLY-Kit شش اعتبارسنج برای داده‌هایی دارد که برنامه‌های ایرانی هر روز با آن‌ها سروکار دارند. همه یک ساختار مشترک دارند؛ پس با یادگرفتن یکی، بقیه را هم می‌شناسید.

کلاسبررسیصفحه
NationalCode۱۰ رقم، رقم کنترل به پیمانهٔ ۱۱، اشارهٔ محل صدورکد ملی
ShebaIR و ۲۴ رقم، ISO 7064 mod-97-10، جست‌وجوی بانکشبا و کارت بانکی
BankCard۱۶ رقم، چک‌سام Luhn، تشخیص بانک از روی BINشبا و کارت بانکی
Mobileقالب 09xxxxxxxxx در پنج شکل ورودی، اشارهٔ اپراتورموبایل، کدپستی، پلاک
PostalCode۱۰ رقم، رقم اول غیر از 0موبایل، کدپستی، پلاک
VehiclePlateقالب پلاک سواری، شکسته‌شده به اجزاموبایل، کدپستی، پلاک

همه در فضای نام RtlyKit\Validation هستند و ارقام فارسی و عربی را همان‌طور که کاربر تایپ کرده می‌پذیرند؛ بنابراین ورودی فرم را بدون پاک‌سازی مستقیم به آن‌ها بدهید.

دو روش فراخوانی#

هر اعتبارسنج هم یک نتیجهٔ بولی می‌دهد و هم یک نتیجهٔ ساخت‌یافته. وقتی فقط «بله یا نه» لازم دارید از isValid() و وقتی می‌خواهید دلیل رد شدن را به کاربر بگویید از validate() استفاده کنید.

<?php
require 'vendor/autoload.php';

use RtlyKit\Validation\NationalCode;
use function RtlyKit\is_national_code;

var_dump(NationalCode::isValid('۰۴۹۹۳۷۰۸۹۹'));   // bool(true)
var_dump(is_national_code('0499370899'));        // bool(true)

$result = NationalCode::validate('0499370898');
var_dump($result->isValid());                    // bool(false)
print_r($result->errors());                      // Array ( [0] => invalid_checksum )

توابع کمکی (is_national_code()، validate_sheba() و مانند آن‌ها) در فضای نام اختصاصی‌اند و با use function RtlyKit\is_national_code; وارد می‌شوند. نام‌های کوتاه سراسری اختیاری است؛ توابع کمکی و نام‌های سراسری را ببینید.

قرارداد Validator#

هر اعتبارسنج RtlyKit\Contracts\Validator را پیاده می‌کند که دقیقاً دو متد ایستا دارد:

  • validate(mixed $value): Result
  • isValid(mixed $value): bool؛ میان‌بر validate($value)->isValid()

اعتبارسنج‌ها بی‌حالت‌اند و برای همین متدها ایستا هستند. به این ترتیب می‌توانید اعتبارسنج را در زمان اجرا با class-string انتخاب کنید، مثلاً از روی یک آرایهٔ پیکربندی:

use RtlyKit\Contracts\Validator;
use RtlyKit\Validation\Mobile;
use RtlyKit\Validation\NationalCode;
use RtlyKit\Validation\PostalCode;

/** @var array<string, class-string<Validator>> $rules */
$rules = [
    'national_code' => NationalCode::class,
    'mobile'        => Mobile::class,
    'postal'        => PostalCode::class,
];
$input = ['national_code' => '0499370899', 'mobile' => '0912', 'postal' => '1234567890'];

foreach ($rules as $field => $class) {
    $result = $class::validate($input[$field]);
    echo $field, ': ', $result->isValid() ? 'ok' : implode(',', $result->errors()), "\n";
}
// national_code: ok
// mobile: invalid_format
// postal: ok
هرگز استثنا پرتاب نمی‌کند. هیچ‌یک از این دو متد برای ورودی بد استثنا نمی‌اندازد. هر مقداری، از جمله null، آرایه، شیء، رشتهٔ خیلی بلند و UTF-8 نامعتبر، یک Result نامعتبر با کلید خطای پایدار می‌دهد. استثنا فقط برای خطای برنامه‌نویس در بخش‌های دیگر کتابخانه است؛ مدیریت خطا را ببینید.

شیء Result#

RtlyKit\Validation\Result یک شیء مقداری تغییرناپذیر با سه متد خواندنی است:

متدمقدار بازگشتی
isValid()bool
errors()list<string>؛ کلیدهای خطای پایدار، در حالت معتبر خالی
details()array<string, mixed>؛ اطلاعاتی که اعتبارسنج در حین بررسی به دست آورده

جزئیات هم در نتیجهٔ معتبر و هم در نتیجهٔ نامعتبر هست (تا جایی که اعتبارسنج پیش رفته)؛ پس می‌توانید مقدار نرمال‌شده یا نام بانک را کنار پیام خطا هم نشان دهید:

use RtlyKit\Validation\BankCard;

$result = BankCard::validate('6037991234567890');
var_dump($result->isValid());   // bool(false)
print_r($result->errors());     // Array ( [0] => invalid_checksum )
echo json_encode($result->details(), JSON_UNESCAPED_UNICODE);
// {"normalized":"6037991234567890","bin":"603799","bank_name":"بانک ملی ایران"}

کلیدهای جزئیات هر اعتبارسنج#

اعتبارسنجکلیدهای جزئیات
NationalCodenormalized، location ({province, city} یا null)
Shebanormalized، bank_code، bank_name
BankCardnormalized، bin، bank_name
Mobilenormalized، operator
PostalCodenormalized
VehiclePlatenormalized و در صورت تطابق قالب: two_digit، letter، three_digit، region

مقدارهای جست‌وجو (location، bank_name، operator) وقتی جدول ورودی نداشته باشد null هستند. نبودن ورودی یعنی «ناشناخته»، نه «نامعتبر».

کلیدهای خطا#

خطاها کلیدهای پایدار و ماشین‌خوان‌اند و میان نسخه‌ها تغییر نمی‌کنند؛ پس می‌توانید آن‌ها را به پیام یا ترجمهٔ خودتان نگاشت کنید. یکپارچگی لاراول دقیقاً همین کار را می‌کند؛ اعتبارسنجی و Cast در لاراول را ببینید.

کلیدمعنامورد استفاده
invalid_typeمقدار رشته، عدد صحیح یا عدد اعشاری صحیح و متناهی نیستهمه
input_too_longرشته‌ای بلندتر از ۴۰۹۶ بایتهمه
invalid_formatقالب نادرست است (نویسه‌ها، تعداد ارقام، الگو)همه؛ در PostalCode برای رقم اول 0
invalid_lengthتعداد ارقام ۱۰ نیستPostalCode
repeated_digitsهمهٔ ارقام یکسان‌اند (1111111111)NationalCode، BankCard
invalid_checksumرقم یا ارقام کنترل نمی‌خواندNationalCode، Sheba، BankCard
invalid_regionیکی از بخش‌های عددی پلاک همه صفر استVehiclePlate

امروز هر نتیجه حداکثر یک خطا دارد (نخستین بررسی ناموفق)، اما errors() فهرست برمی‌گرداند تا بررسی‌های آینده بتوانند چند خطا گزارش کنند.

پردازش ورودی#

پیش از اجرای هر قاعده، مقدار از یک دروازهٔ مشترک می‌گذرد:

  • رشته‌ها تا ۴۰۹۶ بایت پذیرفته می‌شوند. هر رقم فارسی یا عربی دو بایت است؛ پس سقف حدود ۲۰۰۰ رقم از این نوع است. رشتهٔ بلندتر input_too_long می‌دهد.
  • int با (string) تبدیل می‌شود.
  • float باید متناهی، صحیح و قدرمطلقش کمتر از 1015 باشد و بدون نمای علمی تبدیل می‌شود. NaN، INF، 1.5 و اعداد خیلی بزرگ invalid_type می‌دهند.
  • هر چیز دیگر، یعنی null، bool، آرایه و شیء، invalid_type می‌دهد.
use RtlyKit\Validation\NationalCode;
use RtlyKit\Validation\PostalCode;

print_r(NationalCode::validate(null)->errors());                  // [invalid_type]
print_r(NationalCode::validate(1.5)->errors());                   // [invalid_type]
print_r(NationalCode::validate(str_repeat('1', 4097))->errors()); // [input_too_long]
print_r(NationalCode::validate("\xff\xfe")->errors());            // [invalid_format]
var_dump(PostalCode::validate(1234567890)->isValid());            // bool(true)
صفر ابتدایی و عدد صحیح. اگر کد ملی یا کدپستی را به صورت عدد صحیح بدهید، صفرهای ابتدایی از بین می‌رود: 499370899 همان 0499370899 نیست و اعتبارسنج فقط نُه رقم را می‌بیند. شناسه‌ها را از فرم یا ستون پایگاه داده تا اعتبارسنج به صورت رشته نگه دارید.

نرمال‌سازی#

پس از دروازه، هر اعتبارسنج رشته را با متد عمومی normalize() خودش نرمال می‌کند. قاعده‌های مشترک:

  • ارقام فارسی (۰-۹) و عربی-هندی (٠-٩) با Digits::toEnglish() به ارقام انگلیسی تبدیل می‌شوند.
  • جداکننده‌هایی که کاربر تایپ می‌کند حذف می‌شود: فاصله، خط تیره و نیم‌فاصله (ZWNJ). Mobile، BankCard و PostalCode فراتر می‌روند و فقط رقم‌ها را نگه می‌دارند.
  • Sheba علاوه بر این حروف را بزرگ می‌کند و به رشتهٔ ۲۴ رقمی خالی پیشوند IR می‌افزاید.

مقدار نرمال‌شده همیشه در details()['normalized'] برمی‌گردد. همان را ذخیره کنید، نه ورودی خام را، تا یک شماره هرگز با دو املا ذخیره نشود.

جدول‌های جست‌وجو و منبع داده#

چهار اعتبارسنج یک جست‌وجو هم دارند: بانک از روی BIN کارت، بانک از روی کد شبا، محل صدور از روی پیش‌شمارهٔ کد ملی و اپراتور از روی پیش‌شمارهٔ موبایل. این جست‌وجوها فقط امکان جانبی‌اند و اعتبار هیچ‌گاه به آن‌ها بستگی ندارد.

  • BIN کارت بانکی: ۳۹ مورد. کد بانک شبا: ۳۸ مورد. پیش‌شمارهٔ کد ملی: ۵۴۷ مورد.
  • یک مورد فقط وقتی وارد جدول می‌شود که دست‌کم دو منبع مستقل با هم موافق باشند. نبودن مورد یعنی ناشناخته.
  • منابع، مجموعه‌داده‌های جامعهٔ توسعه‌دهندگان و جدول‌های عمومی‌اند. بعضی از آن‌ها ریشهٔ مشترک دارند؛ پس توافق‌شان قوی است اما کاملاً مستقل نیست.
محدودیت شناخته‌شده. جدول‌های جست‌وجو داده‌های «تا حد امکان درست» هستند و فهرست رسمی نیستند. بانک‌ها ادغام و تغییر نام می‌دهند و اپراتورها قابل‌حمل‌اند. نتیجهٔ جست‌وجو را به عنوان اشاره نشان دهید و تصمیم حقوقی، مالی یا هویتی را بر آن بنا نکنید. منبع‌ها، تاریخ‌ها و هشدارها در دقت و داده‌ها آمده است.

ادامه#

  • کد ملی: الگوریتم، نرمال‌سازی و اشارهٔ محل صدور.
  • شبا و کارت بانکی: mod-97 و Luhn و تشخیص بانک.
  • موبایل، کدپستی و پلاک خودرو.
  • سقف‌ها: همهٔ محدودیت‌های اندازه در یک جا.
