Install and auto-discovery#

Nothing is needed beyond Composer. The package declares its provider and facade alias in composer.json under extra.laravel, so Laravel's package discovery registers them on the next composer install or composer update.

composer require enaxon/rtly-kit

The integration uses the Laravel components illuminate/support, illuminate/translation, illuminate/validation and illuminate/database, which a Laravel application already has. The test suite runs against these components at version 11 and 12 (the development constraint is ^11.0||^12.0); the library itself needs only PHP 8.2 and works without Laravel.

Note. The integration tests exercise the real container, translator, validation factory and Eloquent model classes, not a full application skeleton. The code samples on these pages were run the same way.

If your application disables discovery for this package ("dont-discover": ["enaxon/rtly-kit"]), register the provider yourself. In Laravel 11 and later add it to bootstrap/providers.php:

return [
    App\Providers\AppServiceProvider::class,
    RtlyKit\Laravel\RtlyKitServiceProvider::class,
];

On older application layouts add the same class to the providers array in config/app.php. There is no configuration file to publish and no migration.

What the service provider does#

RtlyKit\Laravel\RtlyKitServiceProvider has one job in each phase:

  • register() binds a singleton under the container key rtly-kit.jalali, a RtlyKit\Laravel\JalaliFactory. This is the object behind the facade.
  • boot() does three things: it installs the Carbon macros (see Carbon macros), loads the package translations under the rtly-kit namespace, and registers the validation rules when the container has a validation factory (see Validation and the cast).
Note. The provider registers no global functions. A test boots it and asserts that none of the 27 short helper names exists afterwards. If you want the short global names, call \RtlyKit\Globals::register() yourself; see helpers and globals.

If the container's validator is not an Illuminate\Validation\Factory (a custom replacement), the provider leaves it untouched and skips the rules instead of failing.

The Jalali facade#

The alias Jalali (class RtlyKit\Laravel\Facades\Jalali) forwards to the factory. It offers four methods that mirror the static constructors of RtlyKit\Calendar\Jalali:

use RtlyKit\Laravel\Facades\Jalali;

echo Jalali::create(1404, 1, 1)->format('Y/m/d l');   // 1404/01/01 جمعه
echo Jalali::make('2025-03-21')->toDateString();       // 1404/01/01
echo get_class(Jalali::now());                         // RtlyKit\Calendar\Jalali
// Jalali::today() is also available

Every call returns an ordinary immutable Jalali object, so everything on the Jalali calendar page applies. The factory is a singleton, so a repeated app('rtly-kit.jalali') returns the same instance.

The facade is optional. In classes you can import the class directly or use the namespaced helper \RtlyKit\jdate(); in tests there is nothing to fake because the factory is stateless.

Translations: fa, en, ar#

The provider calls loadTranslationsFrom() with the rtly-kit namespace, so the messages live in rtly-kit::validation.* and follow the application locale. There are three complete sets, one line per rule:

Keyfaen
national_code:attribute کد ملی معتبر نیست.The :attribute is not a valid Iranian national code.
sheba:attribute شماره شبا معتبر نیست.The :attribute is not a valid Iranian Sheba (IBAN).
bank_card:attribute شماره کارت بانکی معتبر نیست.The :attribute is not a valid Iranian bank card.
iran_mobile, mobile:attribute شماره موبایل معتبر نیست.The :attribute is not a valid Iranian mobile number.
postal_code:attribute کد پستی معتبر نیست.The :attribute is not a valid Iranian postal code.
vehicle_plate:attribute پلاک خودرو معتبر نیست.The :attribute is not a valid Iranian vehicle plate.

The Arabic file is resources/lang/ar/validation.php in the package, with the same keys. The same rule in three locales:

// field named national_code, value '1234567890', rule national_code
// locale fa: national code کد ملی معتبر نیست.
// locale en: The national code is not a valid Iranian national code.
// locale ar: national code ليس رقماً وطنياً إيرانياً صالحاً.

(Laravel turns the field name national_code into the attribute label "national code"; give the field a proper label through the attributes translations to get a natural sentence.)

If the active locale has no line, Laravel's normal fallback locale (app.fallback_locale) is used. If no translation can be found at all, the built-in English text is the last resort.

Overriding a message#

You do not publish anything. Choose whichever fits, from the narrowest to the widest:

  1. Per validation call: pass custom messages to the validator or to $request->validate() in the usual way, for example key postal_code or zip.postal_code. A custom message always wins.
  2. Application-wide: add the rule's line to your own lang/fa/validation.php (the key is the rule name, for example 'sheba' => 'شبای :attribute اشتباه است.'). The application's validation.<rule> line is preferred over the package's.
  3. Replace the package texts: create lang/vendor/rtly-kit/fa/validation.php (or en, ar). Laravel's standard vendor-override mechanism loads it over the package file; you only need the keys you change.

Verified output for options 2 and 3 with the locale fa:

// lang/vendor/rtly-kit/fa/validation.php  ->  ['national_code' => 'کد ملی :attribute درست نیست.']
// lang/fa/validation.php                  ->  ['sheba' => 'شبای :attribute اشتباه است.']
// custom message on the call              ->  ['postal_code' => 'کد پستی :attribute نادرست']
//
// national_code: کد ملی x درست نیست.
// sheba:         شبای x اشتباه است.
// postal_code:   کد پستی x نادرست

The field in these examples is named x, which is why x appears in the sentences. In a real form, set readable labels in the attributes array of your validation.php.

Configuration#

There is no config file. Behaviour is fixed by design and by the locale of the application. The library reads the default time zone from PHP (date_default_timezone_get()), which Laravel sets from config('app.timezone'), so Jalali::now() follows your application time zone.

Known limitation. If the validation factory is not bound when the provider boots, the rules are not registered; they are not registered lazily later. This only happens in unusual bootstraps (for example a console-only container without the validation service).
