هر پاسخِ زیر با کد تطبیق داده شده و نمونه‌ها اجرا شده‌اند. اگر مشکلتان اینجا نیست، ابتدا مدیریت خطا (معنای هر کد استثنا) و محدودیت‌ها را ببینید.

نصب و توابع کمکی

خطای «Call to undefined function jdate()» می‌گیرم. توابع کمکی کجایند؟

توابع کمکی توابع فضای‌نام‌دار RtlyKit هستند و بسته به‌طور پیش‌فرض هیچ تابع سراسری تعریف نمی‌کند تا هرگز با کد شما یا بستهٔ دیگری تداخل نکند. توابعی را که لازم دارید import کنید، با نام کامل صدا بزنید، یا یک بار هنگام راه‌اندازی نام‌های کوتاه سراسری را فعال کنید:

<?php
require __DIR__.'/vendor/autoload.php';

use function RtlyKit\jdate;                       // راه ۱: import
echo jdate('2026-03-21')->format('Y/m/d'), "\n";  // 1405/01/01

echo \RtlyKit\jdate('2026-03-21')->format('Y/m/d'), "\n";  // راه ۲: نام کامل

$skipped = \RtlyKit\Globals::register();          // راه ۳: نام‌های کوتاه سراسری
echo \jdate('2026-03-21')->format('Y/m/d'), "\n";  // 1405/01/01
var_dump($skipped);                               // array(0) {} (نام اشغال‌شده‌ای نبود)

‏Globals::register() هرگز تابع موجودی را بازنویسی نمی‌کند و هرگز استثنا پرتاب نمی‌کند؛ نام‌هایی را که رد کرده برمی‌گرداند تا ثبتشان کنید. در Blade یا \RtlyKit\jdate(...) را صدا بزنید یا سراسری‌ها را از AppServiceProvider::register() ثبت کنید. ارائه‌دهندهٔ سرویس لاراول آن‌ها را برایتان ثبت نمی‌کند. به توابع کمکی و سراسری‌ها نگاه کنید.

کدام استثنا را بگیرم؟

برای کل کتابخانه RtlyKit\Exceptions\RtlyKitThrowable (یا RtlyKitException) را بگیرید، یا یک زیرکلاس مشخص مثل InvalidDateException. اعتبارسنج‌ها اصلاً استثنا پرتاب نمی‌کنند و به try نیاز ندارند. بر اساس getErrorCode() تصمیم بگیرید، نه متن پیام. جزئیات در مدیریت خطا.

تقویم‌ها

شمارهٔ روز هفته در جلالی و هجری فرق دارد

عمدی است. Jalali::getDayOfWeek() (و نشانهٔ قالب w) از شنبه، اولین روز هفتهٔ ایرانی، می‌شمارد: شنبه ۰ و جمعه ۶. Hijri و Hebrew مثل date('w') در PHP از یکشنبه شروع می‌کنند، پس شنبه ۶ است. برای یک روز، 2026-03-21 (شنبه):

use function RtlyKit\{jdate, hdate, hebrew_date};

echo jdate('2026-03-21')->getDayOfWeek(), ' ',
     hdate('2026-03-21')->getDayOfWeek(), ' ',
     hebrew_date('2026-03-21')->getDayOfWeek(), "\n";   // 0 6 6

اگر شماره‌گذاری یکسان می‌خواهید، با toGregorian()->format('w') از طریق میلادی بگیرید.

jdate('1405-01-01') و jdate('2026-03-21') هر دو کار می‌کنند، اما سال میلادیِ ۹۹۹ نه

رشته‌ای به شکل Y/m/d یا Y-m-d اگر سالش کمتر از ۱۷۰۰ باشد تاریخِ خودِ همان تقویم خوانده می‌شود (برای Hijri هم همین؛ برای Hebrew سال ۳۰۰۰ یا بیشتر)، وگرنه میلادی. پس تاریخ میلادیِ واقعی با سال کوچک اشتباه خوانده می‌شود. به‌جای رشته یک DateTimeImmutable بدهید که هیچ‌گاه بازتفسیر نمی‌شود:

use function RtlyKit\jdate;

echo jdate('2026-03-21')->format('Y/m/d'), "\n";                              // 1405/01/01 (سال >= 1700: میلادی)
echo jdate('1405-01-01')->toGregorian()->format('Y-m-d'), "\n";               // 2026-03-21 (سال < 1700: جلالی)
echo jdate('0999-01-01')->format('Y/m/d'), "\n";                              // 0999/01/01 (سال جلالی 999)
echo jdate(new DateTimeImmutable('0999-01-01'))->format('Y/m/d'), "\n";       // 0377/10/11 (سال میلادی 999)

ارقام فارسی و عربی ابتدا نرمال می‌شوند، پس '۱۴۰۴/۰۱/۰۱' کار می‌کند. رشتهٔ خالی InvalidDateException پرتاب می‌کند و null یعنی «اکنون».

format() رقم انگلیسی چاپ می‌کند. رقم فارسی چطور؟

قالب‌بندی عمداً رقم لاتین برمی‌گرداند تا نتیجه برای پایگاه داده و URL امن باشد. هنگام نمایش، خروجی را تبدیل کنید:

use function RtlyKit\{jdate, to_persian};

echo jdate('2026-03-21')->format('Y/m/d'), "\n";               // 1405/01/01
echo to_persian(jdate('2026-03-21')->format('Y/m/d')), "\n";   // ۱۴۰۵/۰۱/۰۱

‏Hijri::format() هم با آرگومان $digits (‏latin، persian یا arabic) می‌تواند خودش رقم را تولید کند.

jdate('1404/12/30') استثنا می‌دهد ولی 1403/12/30 نه

اسفند فقط در سال کبیسه ۳۰ روز دارد. ۱۴۰۳ کبیسه و ۱۴۰۴ غیرکبیسه است؛ پس ۱۴۰۴/۱۲/۳۰ وجود ندارد و InvalidDateException با کد invalid_date پرتاب می‌شود. ماه ۱۳ یا روز ۳۱ در ماه‌های نیمهٔ دوم سال (مثل ۱۴۰۴/۰۷/۳۱) هم همین‌طور است.

«امروز» برای کاربرانم یک روز اختلاف دارد

‏jdate() بدون آرگومان از منطقهٔ زمانی پیش‌فرض PHP (‏date_default_timezone_get()، روی سرورها اغلب UTC) استفاده می‌کند. نزدیک نیمه‌شب به وقت تهران، آن روز جلالیِ قبل یا بعد است. یک DateTimeZone بدهید یا منطقهٔ زمانی پیش‌فرض برنامه را تنظیم کنید. آرگومان منطقهٔ زمانی یک لحظهٔ ورودی را تبدیل می‌کند:

use function RtlyKit\jdate;

$utc = new DateTimeImmutable('2026-03-20 22:00', new DateTimeZone('UTC'));

echo jdate($utc)->format('Y/m/d H:i'), "\n";                                       // 1404/12/29 22:00
echo jdate($utc, new DateTimeZone('Asia/Tehran'))->format('Y/m/d H:i'), "\n";    // 1405/01/01 01:30

برای سال دور آینده یا عدد بسیار بزرگ InvalidDateException می‌گیرم

هر تقویم بازهٔ ثابتی دارد (جلالی ‎-620 تا 9377، هجری 1 تا 9665، عبری 3762 تا 13759؛ میلادی 1 تا 9999) و مقدارهای بسیار بزرگ در add*() و timestampها رد می‌شوند. عمدی است: استثنا می‌گیرید، نه تاریخ سرریزشده. به محدودیت‌ها نگاه کنید.

تاریخ هجری یک روز با اعلام محلی ما فرق دارد

‏Hijri از تقویم ام‌القری (تقویم مدنی عربستان) استفاده می‌کند که از پیش محاسبه می‌شود. مراجع محلی رؤیت هلال، از جمله ایران، ممکن است ماه را یک یا دو روز دیرتر شروع کنند. جدول داخلی سال‌های ۱۳۰۰ تا ۱۵۰۰ هجری قمری را پوشش می‌دهد؛ بیرون از آن و برای HijriVariant::Tabular تاریخ حسابی است و ممکن است یک یا دو روز با رؤیت فرق کند. به تقویم هجری و دقت و داده‌ها نگاه کنید.

Carbon و لاراول

روی شیء Carbon خطای «undefined method toJalali()» می‌گیرم

ماکروهای Carbon (‏toJalali، jformat، createFromJalali، toHijri، toHebrew، createFromHijri، createFromHebrew) فقط وقتی ثبت می‌شوند که nesbot/carbon (نسخهٔ ۳) نصب باشد. Composer آن را فقط پیشنهاد می‌کند، پس خودتان نصب کنید: composer require nesbot/carbon. ماکروها وقتی فایل توابع کمکیِ بسته توسط autoloader در Composer بارگذاری شود (و دوباره هنگام boot توسط ارائه‌دهندهٔ لاراول) برای Carbon و CarbonImmutable ثبت می‌شوند. کلاس Illuminate\Support\Carbon لاراول از Carbon ارث می‌برد، پس آن هم کار می‌کند:

use Carbon\Carbon;

echo Carbon::parse('2026-03-21')->toJalali()->format('Y/m/d'), "\n";   // 1405/01/01
echo Carbon::createFromJalali(1405, 1, 1)->toDateString(), "\n";       // 2026-03-21
var_dump(Carbon::hasMacro('toJalali'));                                // bool(true)

اگر hasMacro() مقدار false داد، Carbon نصب نیست یا نسخهٔ major پشتیبانی‌نشده است. به ماکروهای Carbon نگاه کنید.

قواعد اعتبارسنجی لاراول (national_code، sheba و ...) پیدا نمی‌شوند

با کشف خودکار بسته (auto-discovery) ارائه‌دهندهٔ سرویس خودش ثبت می‌شود. اگر کشف خودکار را برای این بسته خاموش کرده‌اید (dont-discover) یا پیکربندیِ کش‌شدهٔ قدیمی دارید، RtlyKit\Laravel\RtlyKitServiceProvider را دستی ثبت کنید و کش‌ها را پاک کنید. نام قواعد: national_code، sheba، bank_card، iran_mobile (با نام مستعار mobile)، postal_code و vehicle_plate است. پیام‌ها به فارسی، انگلیسی و عربی همراه بسته‌اند و از app()->getLocale() پیروی می‌کنند؛ خطوط lang/{locale}/validation.php خودتان همچنان اولویت دارند. به راه‌اندازی لاراول نگاه کنید.

مدل الکوئنت هنگام انتساب تاریخ InvalidDateException پرتاب می‌کند

‏JalaliCast یک Jalali، هر DateTimeInterface، timestamp یونیکس، رشتهٔ میلادی یا رشتهٔ جلالی مثل 1404/01/15 10:30 را می‌پذیرد (ارقام فارسی و جداکنندهٔ / یا - مجاز است). هر چیز دیگر خطاست: تاریخ غیرممکن، متن بی‌معنی و مقادیر غیرسکالر (مثل آرایه) هنگام انتساب InvalidDateException پرتاب می‌کنند. null و رشتهٔ خالی به null تبدیل می‌شوند. آن را در Form Request یا کنترلر بگیرید:

$post->published_at = '1404/01/15 10:30';   // ذخیره می‌شود: 2025-04-04 10:30:00
$post->published_at = '1404/13/45';         // InvalidDateException (invalid_date)
$post->published_at = 'hello';              // InvalidDateException (invalid_date)
$post->published_at = ['x'];                // InvalidDateException (invalid_date)

ستون را یک datetime میلادیِ عادی نگه دارید: cast مقدار Y-m-d H:i:s را می‌نویسد و آن را به‌صورت یک Jalali تغییرناپذیر می‌خواند. cast هیچ تبدیل منطقهٔ زمانی انجام نمی‌دهد. به اعتبارسنجی و cast در لاراول نگاه کنید.

اعتبارسنج‌ها و داده

is_national_code(13542419) برابر false است ولی نسخهٔ رشته‌ای true

یک int صفرهای ابتدایی را از قبل از دست داده است: 0013542419 شده 13542419، هشت رقم. اعتبارسنج‌ها عدد صحیح را به رشته تبدیل می‌کنند ولی نمی‌توانند صفرها را برگردانند. شناسه‌ها را همه‌جا (فیلد فرم، JSON، ستون پایگاه داده) به‌صورت رشته نگه دارید:

use function RtlyKit\is_national_code;

var_dump(is_national_code(13542419));       // bool(false)
var_dump(is_national_code('0013542419'));   // bool(true)

برای کارت یا شبای معتبر، getBankName() مقدار null می‌دهد

جدول‌های BIN، کد شبا و اپراتور فقط ورودی‌هایی دارند که دست‌کم دو منبع تأیید کرده‌اند؛ پس عمداً ناقص‌اند (۳۹ BIN و ۳۸ کد شبا). null یعنی «نامعلوم»، نه «نامعتبر»؛ اعتبار کارت از چک‌سام Luhn و اعتبار شبا از mod-97 می‌آید، مستقل از جدول‌ها. دربارهٔ NationalCode::getLocation() (۵۴۷ پیش‌شماره) هم همین است و محلی که می‌دهد جای صدور است، نه زادگاه. هرگز به‌خاطر null بودن یک نام، کاربر را رد نکنید. به دقت و داده‌ها نگاه کنید.

چرا اعتبارسنج حتی برای null یا آرایه استثنا نمی‌دهد؟

عمدی است: اعتبارسنج‌ها mixed می‌گیرند و با false یا Result نامعتبر پاسخ می‌دهند (‏invalid_type برای مقادیر غیرسکالر، ‏input_too_long بالاتر از ۴۰۹۶ بایت)؛ پس می‌توانید ورودی خام درخواست را مستقیم بدهید. به مرور اعتبارسنج‌ها نگاه کنید.

عدد و متن

format_number(1234567.891) دنبالهٔ بلندی از رقم چاپ می‌کند

‏float در PHP نمی‌تواند 1234567.891 را دقیق نگه دارد و قالب‌بند مقدار دقیقِ ذخیره‌شده را چاپ می‌کند. اعشار را به‌صورت رشته بدهید یا پیش‌تر گرد کنید:

use function RtlyKit\format_number;

echo format_number('1234567.891'), "\n";   // ۱٬۲۳۴٬۵۶۷٫۸۹۱
echo format_number(1234567.891), "\n";     // ۱٬۲۳۴٬۵۶۷٫۸۹۱۰۰۰۰۰۰۰۶۱۴۶۷

number_to_words() برای 1.5، برای اعداد بزرگ عربی و برای زبان‌های دیگر استثنا می‌دهد

اعداد به حروف فقط برای اعداد صحیح تعریف شده‌اند (‏1.5، NaN و INF استثنای InvalidNumberException می‌دهند؛ float صحیحی مثل 3.0 پذیرفته است). فارسی تا ۲۱ رقم می‌رود و عربی تا 999,999,999 به شکل شمارشِ مذکر و بدون اعراب پایانی. فقط fa و ar وجود دارند؛ هر زبان دیگر UnsupportedLocaleException پرتاب می‌کند. به اعداد به حروف و محدودیت‌ها نگاه کنید.

اوقات شرعی و تعطیلات

اوقات شرعی در منطقهٔ زمانی اشتباه است یا یک ساعت جابه‌جا

زمان‌ها به‌صورت HH:MM و به وقت محلیِ منطقهٔ زمانی محاسبه‌گر هستند، برای روز تقویمیِ محلیِ تاریخی که می‌دهید. PrayerTimes::forCity() از منطقهٔ خود شهر استفاده می‌کند. محاسبه‌گری که با new PrayerTimes() و بدون منطقه ساخته شود از پیش‌فرض PHP (‏date_default_timezone_get()، که در یک کانتینر تازه UTC است) استفاده می‌کند، پس یک DateTimeZone بدهید. ساعت تابستانی برای هر رویداد جداگانه اعمال می‌شود؛ پس جدولی که از تغییر ساعت عبور کند دو طرفش درست است (ظهر قاهره در 2026-10-08 و 2026-10-31):

use RtlyKit\Prayer\PrayerTimes;

$cairo = PrayerTimes::forCity('cairo', PrayerTimes::METHOD_EGYPT);

echo $cairo->getTimes(new DateTimeImmutable('2026-10-08'))['dhuhr'], ' ',   // 12:43 (ساعت تابستانی)
     $cairo->getTimes(new DateTimeImmutable('2026-10-31'))['dhuhr'], "\n";   // 11:39 (ساعت استاندارد)

تاریخی که در منطقهٔ دیگری بدهید ابتدا به منطقهٔ محاسبه‌گر تبدیل می‌شود: 2026-03-20 23:30 به وقت UTC و 2026-03-21 03:00 به وقت Asia/Tehran هر دو اوقات ۲۱ مارس را برای تهران می‌دهند.

بعضی از اوقات شرعی null هستند

در عرض‌های جغرافیایی بالا ممکن است خورشید در یک روز هرگز به زاویهٔ لازم برای فجر، طلوع، مغرب یا عشا نرسد و آن مقدارها null باشند (و عصر در شب قطبی null است). این یک نتیجه است، نه خطا. در رابط کاربری آن را مدیریت کنید:

use RtlyKit\Prayer\PrayerTimes;

$oslo = new PrayerTimes(69.65, 18.96, PrayerTimes::METHOD_MWL, PrayerTimes::ASR_STANDARD, new DateTimeZone('Europe/Oslo'));
echo json_encode($oslo->getTimes(new DateTimeImmutable('2026-06-21'))), "\n";
// {"fajr":null,"sunrise":null,"dhuhr":"12:46","asr":"17:58","maghrib":null,"isha":null}

nextPrayer() زمانی برگرداند که مال فرداست

پس از عشا، nextPrayer() به فجر فردا می‌رود. نتیجه کلید date (‏Y-m-d) دارد که می‌گوید آن نماز مال کدام روز است:

use RtlyKit\Prayer\PrayerTimes;

$next = PrayerTimes::forCity('tehran')->nextPrayer(new DateTimeImmutable('2026-03-21 23:00', new DateTimeZone('Asia/Tehran')));
echo json_encode($next), "\n";   // {"name":"fajr","time":"04:42","date":"2026-03-22"}

اوقات من چند دقیقه با مسجد یا برنامهٔ دیگر فرق دارد

مراجع مختلف زاویه‌های گرگ‌ومیش و گردکردن متفاوتی دارند. برای روش‌های راستی‌آزمایی‌شده محاسبه تا حدود یک دقیقه با جدول‌های منتشرشده می‌خواند، اما زاویه‌های کراچی، MWL و ISNA و نیز عشا و عصرِ روش تهران با جدول رسمی سنجیده نشده‌اند. روشی را برگزینید که جامعهٔ شما دنبال می‌کند، ضریب عصر را تنظیم کنید (‏ASR_HANAFI عصر را دیرتر می‌کند) و برای جاهای مرتفع آرگومان ارتفاع را بدهید. به اوقات شرعی و دقت و داده‌ها نگاه کنید.

یک مناسبت مذهبی یک روز با تقویم رسمی فرق دارد

مناسبت‌های اسلامی از تقویم هجری محاسبه می‌شوند، در حالی که ایران آن‌ها را با رؤیت هلال اعلام می‌کند؛ پس ممکن است ۱ یا ۲ روز اختلاف داشته باشند. تعطیلات ثابت جلالی (مثل نوروز و ۲۲ بهمن) دقیق‌اند. بیرون از ۱۳۰۰ تا ۱۵۰۰ هجری قمری فقط تعطیلات ثابت گزارش می‌شود. اگر دقت برای حقوق و مهلت‌ها حیاتی است، از سمت خودتان فهرست بازنویسی را از اعلام رسمی اضافه کنید. به تعطیلات نگاه کنید.
