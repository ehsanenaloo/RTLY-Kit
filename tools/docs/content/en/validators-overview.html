The six validators

RTLY-Kit ships six validators for data that Iranian applications handle every day. They all follow one shape, so once you know one you know them all.

ClassChecksPage
NationalCode10 digits, mod-11 check digit, place-of-issue hintNational code
ShebaIR + 24 digits, ISO 7064 mod-97-10, bank lookupSheba and bank card
BankCard16 digits, Luhn checksum, bank lookup by BINSheba and bank card
MobileShape of 09xxxxxxxxx in five input forms, operator hintMobile, postal code, plate
PostalCode10 digits, first digit not 0Mobile, postal code, plate
VehiclePlatePassenger-car plate shape, parsed into partsMobile, postal code, plate

All of them live in the RtlyKit\Validation namespace and accept Persian and Arabic digits as typed by users, so you can pass form input straight in without cleaning it first.

Two ways to call

Every validator offers a plain boolean and a structured result. Use isValid() when you only need yes or no, and validate() when you want to tell the user why a value was rejected.

<?php
require 'vendor/autoload.php';

use RtlyKit\Validation\NationalCode;
use function RtlyKit\is_national_code;

var_dump(NationalCode::isValid('۰۴۹۹۳۷۰۸۹۹'));   // bool(true)
var_dump(is_national_code('0499370899'));        // bool(true)

$result = NationalCode::validate('0499370898');
var_dump($result->isValid());                    // bool(false)
print_r($result->errors());                      // Array ( [0] => invalid_checksum )

The helpers (is_national_code(), validate_sheba(), and so on) are namespaced; import them with use function RtlyKit\is_national_code;. Short global names are opt-in; see Helpers and globals.

The Validator contract

Every validator implements RtlyKit\Contracts\Validator, which has exactly two static methods:

  • validate(mixed $value): Result
  • isValid(mixed $value): bool, a shortcut for validate($value)->isValid()

Validators are stateless, so the methods are static. That makes it easy to pick a validator at runtime through a class-string, for example from a configuration array:

use RtlyKit\Contracts\Validator;
use RtlyKit\Validation\Mobile;
use RtlyKit\Validation\NationalCode;
use RtlyKit\Validation\PostalCode;

/** @var array<string, class-string<Validator>> $rules */
$rules = [
    'national_code' => NationalCode::class,
    'mobile'        => Mobile::class,
    'postal'        => PostalCode::class,
];
$input = ['national_code' => '0499370899', 'mobile' => '0912', 'postal' => '1234567890'];

foreach ($rules as $field => $class) {
    $result = $class::validate($input[$field]);
    echo $field, ': ', $result->isValid() ? 'ok' : implode(',', $result->errors()), "\n";
}
// national_code: ok
// mobile: invalid_format
// postal: ok
Never throws. Neither method throws for bad input. Any value, including null, arrays, objects, oversized strings and invalid UTF-8, produces an invalid Result with a stable error key. Exceptions are reserved for programmer errors elsewhere in the library; see Error handling.

The Result object

RtlyKit\Validation\Result is an immutable value object with three read methods:

MethodReturns
isValid()bool
errors()list<string>: stable error keys, empty when valid
details()array<string, mixed>: facts the validator learned while checking

The details are present on both valid and invalid results (as far as the validator got before it stopped), so you can display the normalized value or a bank name even next to an error:

use RtlyKit\Validation\BankCard;

$result = BankCard::validate('6037991234567890');
var_dump($result->isValid());   // bool(false)
print_r($result->errors());     // Array ( [0] => invalid_checksum )
echo json_encode($result->details(), JSON_UNESCAPED_UNICODE);
// {"normalized":"6037991234567890","bin":"603799","bank_name":"بانک ملی ایران"}

Detail keys per validator

ValidatorDetail keys
NationalCodenormalized, location ({province, city} or null)

Lookup values (location, bank_name, operator) are null when the table has no entry. A missing entry means "unknown", never "invalid".

Error keys

Errors are stable, machine-readable keys. They do not change between releases, so you can map them to your own messages or translations. The Laravel integration does exactly that; see Laravel validation and cast.

KeyMeaningUsed by
invalid_typeThe value is not a string, an int, or an integral finite floatall
input_too_longA string longer than 4096 bytesall
invalid_formatThe shape is wrong (character set, digit count, pattern)all except PostalCode, which uses it for a leading 0
invalid_lengthThe digit count is not 10PostalCode
repeated_digitsEvery digit is the same (1111111111)NationalCode, BankCard
invalid_checksumThe check digit or check digits do not matchNationalCode, Sheba, BankCard
invalid_regionA numeric part of the plate is all zerosVehiclePlate

A result carries at most one error today (the first check that failed), but errors() returns a list so that future checks can report several.

Input handling

Before any rule runs, the value goes through one shared gate:

  • Strings up to 4096 bytes pass. Persian and Arabic digits take two bytes each, so the cap is about 2000 such digits. A longer string yields input_too_long.
  • int is converted with (string).
  • float must be finite, integral, and below 1015 in magnitude; it is converted without an exponent. NaN, INF, 1.5 and huge floats yield invalid_type.
  • Everything else, namely null, bool, arrays and objects, yields invalid_type.
use RtlyKit\Validation\NationalCode;
use RtlyKit\Validation\PostalCode;

print_r(NationalCode::validate(null)->errors());                  // [invalid_type]
print_r(NationalCode::validate(1.5)->errors());                   // [invalid_type]
print_r(NationalCode::validate(str_repeat('1', 4097))->errors()); // [input_too_long]
print_r(NationalCode::validate("\xff\xfe")->errors());            // [invalid_format]
var_dump(PostalCode::validate(1234567890)->isValid());            // bool(true)
Leading zeros and numbers. Passing a national code or postal code as an integer loses leading zeros: 499370899 is not 0499370899, and the validator can only see the nine digits. Keep identifiers as strings from the form or database column all the way to the validator.

Normalization

After the gate, each validator normalizes the string with its own public normalize() method. They share these rules:

  • Persian (۰-۹) and Arabic-Indic (٠-٩) digits become English digits, using Digits::toEnglish().
  • Separators users type are removed: spaces, hyphens, and the half-space (ZWNJ). Mobile, BankCard and PostalCode go further and keep only digits.
  • Sheba also upper-cases the text and adds the IR prefix to a bare 24-digit string.

The normalized value is always returned in details()['normalized']. Store that, not the raw input, so the same number is never saved in two spellings.

Lookup tables and their provenance

Four validators attach a lookup: bank by card BIN, bank by Sheba code, place of issue by national-code prefix, and operator by mobile prefix. The lookups are conveniences on top of validation; validity itself never depends on them.

  • Bank card BINs: 39 entries. Sheba bank codes: 38 entries. National-code prefixes: 547 entries.
  • An entry is included only when at least two independent sources agree. Missing entry means unknown.
  • The sources are community datasets and public tables. Some of them share ancestry, so agreement is strong but not fully independent.
Known limitation. The lookup tables are best-effort data, not an official registry. Banks merge and rename, and operators are portable. Show a lookup result as a hint, and do not base legal, financial or identity decisions on it. Sources, dates and caveats are listed in Accuracy and data.
